# Batch 4 — checkout (highest risk)

Written before implementation, per `CLAUDE.md`'s "Discuss / Plan" step.

> **Revised after review (20 September 2026).** The session-pinned cart item IDs described below were replaced by a review fingerprint posted with the form, after independent review findings CHK-001 and CHK-002. The pin, `SESSION_ITEM_IDS` and the "item added after the review page stays in the cart" behaviour no longer apply; see [checkout-review-fixes.md](checkout-review-fixes.md). The rest of this plan (locking order, savepoint handling, exception mapping, live-price rule) still holds.

## Context

Next roadmap batch after cart (Batch 3, shipped on `erfan/backend-auth`). Checkout turns a cart into a real `Order` — the highest-risk batch so far, because `Order`/`OrderItem` are already schema-locked with PostgreSQL constraints/triggers (`src/orders/models.py`, `src/reporting/migrations/0002_inventory_guards.py`) and `docs/SCHEMA.md`'s "Checkout transaction" section (lines 37-45) already dictates the sequence non-negotiably. `docs/API.md` only reserves `POST /checkout/` — everything else (route names, page structure, the idempotency mechanism) is ours to design, and was discussed with the user before writing this.

`src/orders/` currently has only the foundation models/migration (`0001_initial.py`) — no views, urls, services, forms, or templates. This batch adds all of them, plus `orders:detail` (pulled forward from the original Batch 5 scope, since checkout needs a confirmation destination and building a throwaway one now would be wasted work).

## Non-negotiable constraints (from `SCHEMA.md` / the models — not decisions, just facts)

- `order_origin_valid`: a live (non-imported) order **must** have `external_id = NULL`, a non-null UUID `idempotency_key`, `request_fingerprint` matching `^[0-9a-f]{64}$`, and `status = "completed"`. No other shape is legal for what this batch creates.
- `order_owner_key_unique`: `UniqueConstraint(owner, idempotency_key)` — never two orders for the same user+key; the same key value is fine across different users.
- `order_item_namespace_guard` (DB trigger): `OrderItem.product.namespace` must equal the parent `Order.namespace`. The app validates this proactively; the trigger is a backstop, not the primary defense.
- `docs/API.md`'s general status-code convention: 403 forbidden/CSRF, 404 inaccessible foreign objects, 409 stock/idempotency conflicts, 503 dependency unavailability. Applies directly to this batch.
- `SCHEMA.md`'s 5-step transaction sequence (authenticate/validate → resolve key+fingerprint, equivalent retry returns original order, changed contents conflict → lock in consistent order, recheck stock atomically, create order+items, deduct stock → enforce the unique key at DB level, handle concurrent conflicts so exactly one order survives → clear the cart transactionally, confirm only after commit, never trust cached stock/prices).
- Testing must use real concurrent PostgreSQL connections (`transaction=True` + threads) to prove locking — nothing in the suite does this yet; this batch introduces it.

## Decisions made (discussed with the user)

1. **Idempotency key is session-based, not a hidden form field.** A hidden field only survives a resubmit of the exact same page load; a reload after an uncertain timeout — the realistic failure case this feature exists for — would mint a fresh key under a naive hidden-field design, defeating the point. Instead: `request.session["checkout_idempotency_key"]`, generated on `GET /checkout/` only when absent and the cart is non-empty; reused across reloads; cleared by the view on any terminal outcome — success, a definitive 409 fingerprint conflict, or the cart going empty (which ends that checkout attempt; a later one deserves a fresh key); a `POST` arriving with no key in session restarts the flow (an HTTP 302 to `GET /checkout/`) rather than minting one inline.
   - **Pinned item IDs share the session but not the key's lifecycle.** `request.session["checkout_item_ids"]` records exactly which `CartItem` PKs the review page showed — refreshed on **every render of the checkout page** (the `GET`, *and* every error re-render from `POST`), unlike the key, which is generated once and reused. The invariant is "the pin always matches what the user is currently looking at"; if an error re-render kept a stale pin, the user would be stuck clicking "Place order" against items that are no longer there, failing identically every time with no way out except manually reloading the page. This is what makes checkout match standard ecommerce behavior: the review page is the contract. An item added to the cart in another tab after the page loaded gets a PK that was never pinned, so it can never be silently swept into an order it was never shown in — it just waits in the cart for the next checkout. See "Design details" for how `POST` uses this pin.
2. **Dedicated, read-only checkout review page** (`GET /checkout/`): items, quantities, live unit prices, total, a "payment is simulated" label, and a "Place order" button that `POST`s to the same URL. No quantity editing here — "back to cart" is the only way to change anything, keeping cart (edit) and checkout (confirm) cleanly separated.
3. **Lands on `orders:detail` (this order's confirmation/receipt) on success, not the cart.** An emptied cart carries no order number or total — a weaker confirmation than what real ecommerce checkouts (including Shopee, once you strip its shipping-status tabs which don't apply to our simpler `completed/cancelled/refunded` status model) actually show. `orders:list` (full history) stays Batch 5's job; `orders:detail` is pulled forward now since checkout needs a landing page regardless.
4. **All-or-nothing checkout** — no partial-cart/per-item selection (unlike Shopee). Any inactive or insufficient-stock item blocks the *entire* order; nothing is silently dropped or auto-adjusted.
5. Direct visit to `/checkout/` with an empty cart → redirect to `cart:detail` with an info message, not an empty review page.
6. A 409 (stock or idempotency conflict) re-renders the checkout page itself with the error, at status 409 — not a redirect — so the user sees what happened and can just retry.
7. No HTMX on checkout — it's a page-to-page flow (review → confirmation), unlike cart's in-place fragment swaps.

## Design details

**Fingerprint** — hashes the cart contents that *produced* the order, deliberately excluding price so price drift alone never causes a spurious conflict:
```python
# namespace is always settings.DEMO_NAMESPACE; pairs come from the locked read (services step 4)
def compute_fingerprint(namespace, pairs):  # pairs: (product.external_id, quantity)
    canonical = namespace + "|" + "|".join(f"{eid}:{qty}" for eid, qty in sorted(pairs))
    return hashlib.sha256(canonical.encode()).hexdigest()
```

**`src/orders/services.py`** — `checkout(user, idempotency_key, item_ids)`, explicit function per `ARCHITECTURE.md:13`, mirroring `cart/services.py`'s style. `item_ids` is the session-pinned set of `CartItem` PKs the review page showed (decision 1) — every step below is scoped to exactly this set, never the whole cart:

Exceptions raised (all view-mapped, see below): `EmptyCartError`, `CartChangedError`, `InactiveProductError`, `InvalidProductError`, `InsufficientStockError`, `CheckoutConflictError`. `CartChangedError` is deliberately distinct from `InvalidProductError` — "the cart isn't what you reviewed" and "this product can't be sold" are different conditions with different messages and different recovery paths.

1. **Resolve the pinned items** (a read, no error yet): `cart.items.filter(pk__in=item_ids).select_related("product")`. The `select_related` here is fine and useful — this is an unlocked read, so the join carries no locking implications (unlike the locked query in step 4).
2. **Look up the existing order before raising anything about cart state**: `Order.objects.filter(owner=user, idempotency_key=idempotency_key).first()`. (This ordering matters: raising on an empty cart before this lookup would make the replay branch unreachable — a duplicate `POST` arriving after a successful checkout, once the cart is empty, would incorrectly raise `EmptyCartError` and bounce the user to an empty cart instead of their existing order.) If found: if the pinned items no longer exist (already consumed by the original commit) **or** the fingerprint computed from step 1's read still matches `order.request_fingerprint`, return the existing order (replay, no new work); if it differs, raise `CheckoutConflictError` (409, decision 6).
3. **No order found, and step 1 resolved nothing** — distinguish two different states rather than reporting both as "empty": if `cart.items.exists()` is false the cart is genuinely empty → `EmptyCartError` (view redirects to `cart:detail`, decision 5); if the cart is non-empty but none of the *pinned* IDs survive, the pin is stale → `CartChangedError`. Reporting "your cart is empty" on a page that visibly contains items is a bug, not a cosmetic issue.
4. Inside `transaction.atomic()`: **re-fetch and lock only the pinned cart items**, with **no `select_related`** — `cart.items.filter(pk__in=item_ids).select_for_update(of=("self",)).order_by("pk")`. Two reasons the join is dropped here:
   - `item.product_id` is a local column, so no join is needed to collect product IDs, and the joined `item.product` objects would be **pre-lock copies** of the very rows being locked — reading `item.product.price`/`.stock` would silently defeat the lock and violate `SCHEMA.md`'s "never use cached stock/prices to authorise checkout". With no join there is no stale copy to reach for by accident.
   - Without a join, `select_for_update()` cannot over-lock `Product` at all. `of=("self",)` is kept as explicit intent, but correctness no longer depends on it being right (by default Django locks every table a query touches, including `select_related()` joins — which would lock `Product` rows in `CartItem.pk` order and can deadlock against the `Product.pk`-ordered lock below).
   If this locked re-fetch doesn't return exactly the pinned set (fewer rows — a pinned item was removed, or the cart was cleared by something concurrent), first re-check for an existing `Order` under this key (now guaranteed consistent, since this transaction only reached this point after any concurrent winner committed) and return it if found — that's the genuine double-submit race. Otherwise raise `CartChangedError` — never silently proceed with a partial set (decision 4).
   Lock the products in a **separate, non-joined** query: `Product.objects.filter(pk__in=product_ids).select_for_update().order_by("pk")` — one batched query, not a loop of per-item locks. This is what guarantees deadlock-safe ordering across different users' transactions. Build `locked = {p.pk: p for p in product_qs}` and read **every** product attribute through `locked[item.product_id]` from here on. For each item recheck `product.active`, `quantity <= product.stock`, and `product.namespace == settings.DEMO_NAMESPACE` — the last is a proactive assertion, not just a defensive comment, since `Order.namespace` is a single field derived from potentially-multiple items; failures raise `InactiveProductError`/`InvalidProductError` (→ 200 with inline error) or `InsufficientStockError` (→ 409). Derive `unit_price` from the locked `product.price`; compute `total` as a `Decimal` sum over the locked prices — **do not reuse `cart/services.py:cart_subtotal()`**, which filters out inactive items (checkout must *block* on them, not silently exclude them) and reads the unlocked `item.product.price`. **Recompute the fingerprint from this locked, pinned read** — this is the value persisted on the `Order`, not step 1's pre-transaction snapshot.
5. Create the `Order` inside a **nested** `atomic()` (a savepoint): `namespace=settings.DEMO_NAMESPACE` (**required** — the field has no default and `order_namespace_nonempty` rejects `""`), `external_id=None` (**must be `None`, never `""`** — `order_origin_valid` requires null, and `order_source_unique` on `(namespace, external_id)` only tolerates many live orders because Postgres treats NULLs as distinct), `status="completed"`, `placed_at=timezone.now()`, plus the resolved key and the step-4 fingerprint. Wrap `except IntegrityError` directly around that `with transaction.atomic():` block with nothing else inside the `try`, mirroring `cart/services.py:add_item`'s shape — **but with a fallback `add_item` doesn't need**: `Order` can violate six different constraints on insert (`order_owner_key_unique`, `order_namespace_nonempty`, `order_origin_valid`, `order_total_nonnegative`, `order_status_valid`, `order_source_unique`), whereas `cart_product_unique` is genuinely the only one `add_item` can hit. So after catching, re-query for the winner's order and **re-raise the original `IntegrityError` if the re-query finds nothing** — otherwise a plain constraint bug (a missing `namespace`, an out-of-range `total`) would be silently misreported as a phantom race and then fail later on a `None` order. Optionally tighten further by checking `exc.__cause__.diag.constraint_name == "order_owner_key_unique"`.
6. On success, `bulk_create` the `OrderItem`s (`external_id=None` — `""` violates `order_item_source_nonempty`; live `unit_price` from the locked products) — one batched call; decrement `.stock` in Python on each already-locked `Product` instance and persist all of them with one `Product.objects.bulk_update(products, ["stock"])` call (not a per-item `.save()` loop); delete the cart items by their **explicit locked PKs** from step 4 (never `cart.items.all().delete()`) — all still inside the outer `atomic()`. Return the order.

**`src/orders/views.py`**:
- `CheckoutView(LoginRequiredMixin, View)` — plain `LoginRequiredMixin`, not cart's `HtmxLoginRequiredMixin`, since checkout is a page-to-page flow (decision 7).
  - **One shared render path.** Every render of the checkout page — the `GET`, and every error re-render from `POST` — goes through a single helper that (a) **redirects to `cart:detail` (clearing key/pin) if the cart is empty at render time**, (b) ensures a session key exists, minting one only if absent, and (c) **refreshes `checkout_item_ids` to the cart's current item PKs**. Putting all three in one place is what keeps "the pin matches what's on screen" and "we never render a checkout page for an empty cart" true everywhere rather than on `GET` only — the error paths need (a) precisely because they fire when the cart moved, and it may have moved all the way to empty.
  - `get()`: run the shared render path, then render `orders/checkout.html` with the cart items, live prices/total, and any per-item warnings (inactive/insufficient stock) so the user isn't surprised — informational only, not blocking; the real gate is the `POST`.
  - `post()`: no session key or no pinned item IDs → **`return redirect("orders:checkout")`** — a real HTTP 302, never `return self.get(request)`, which would render the review page as the response to a `POST` and leave a browser refresh re-submitting it (exactly the double-submit this batch exists to prevent). Otherwise call `services.checkout(request.user, key, item_ids)` and map every exception it can raise — an unmapped one is a 500:
    | Raised | Response | Key / pin |
    |---|---|---|
    | `EmptyCartError` | redirect to `cart:detail` (decision 5) | cleared |
    | `CartChangedError` | re-render at **200**, "your cart changed, please review again" | key kept, pin refreshed |
    | `InactiveProductError` / `InvalidProductError` | re-render at **200** with the error | key kept, pin refreshed |
    | `InsufficientStockError` | re-render at **409** (decision 6) | key kept, pin refreshed |
    | `CheckoutConflictError` | re-render at **409** (decision 6) | old key cleared, then a fresh key + pin minted by the shared render path |
    | *(success)* | redirect to `orders:detail` | cleared |
    Two things this table settles that the earlier draft left open: a stock 409 **keeps** the key (the shortfall is transient and the user may legitimately retry — only the fingerprint conflict is "definitive" per decision 1, and minting a new key on a stock retry would break `docs/API.md`'s "never create a new key automatically" rule); and the fingerprint conflict clears the dead key but immediately mints a fresh one as part of rendering, so the 409 page the user is looking at is usable with one click rather than bouncing them through a redirect first. Minting there is consistent with `API.md`, which forbids auto-minting after a *timeout*, not after a definitive conflict.
- `OrderDetailView(LoginRequiredMixin, View)`: `get_object_or_404(Order, pk=pk, owner=request.user)` (404 for foreign, matching the existing project-wide convention), renders `orders/detail.html` (order number, items, total, placed date, simulated-payment note, "Continue shopping" link to the catalogue).

**No Django form is needed for checkout**, and that is deliberate rather than an oversight of `docs/API.md:28` ("use Django forms/validation and CSRF on all browser mutations"). The `POST` body carries nothing but the CSRF token — the idempotency key and pinned item IDs come from the session, and quantities, prices, totals and owner are all derived server-side from locked rows. There is no user-supplied input to validate, which is the strongest possible form of the same document's "derive identity/prices/totals server-side". CSRF still applies via the standard middleware.

**Routing**: `src/orders/urls.py` (new), `app_name = "orders"`, `path("checkout/", CheckoutView.as_view(), name="checkout")` and `path("orders/<int:pk>/", OrderDetailView.as_view(), name="detail")` — two different top-level prefixes under one app, so it's registered at root: `path("", include("orders.urls"))` in `src/config/urls.py`, the same pattern already used for `accounts.urls`.

**Templates** (new, minimal/functional, reusing `.operator-table`/`.operator-row` for the item list like cart did rather than inventing new CSS): `orders/checkout.html`, `orders/detail.html`.

## Tests (`tests/test_orders.py`, new)

Non-concurrent (standard `django_db`): successful checkout creates a correctly-shaped `Order`/`OrderItem`s, decrements stock, clears the cart, redirects to `orders:detail`; unit price captured is the live price at checkout time; empty cart at `GET` redirects to cart; inactive product blocks the whole order (200, no mutation); insufficient stock blocks it (409, no mutation); replay with cart already cleared returns the original order; replay with fingerprint still matching returns the original order; fingerprint mismatch → 409 and no new order; unauthenticated → login redirect; foreign order via `orders:detail` → 404, owner's own → 200; CSRF-missing `POST` → 403; **an item added to the cart after `GET /checkout/` rendered is not included in the order and remains in the cart afterward** (pin-scoping, decision 1/ecommerce-parity); **a pinned item removed from the cart before `POST` blocks the order with a "cart changed" message, no mutation, and the retry after re-rendering succeeds** (proves the pin refresh in the error path — without it the retry would fail identically forever); **a stale pin against a non-empty cart reports "cart changed", not "cart is empty"**.

**Two sequential successful checkouts** deserves its own test and is easy to omit: every live order shares one namespace with `external_id=NULL`, so `order_source_unique` only permits more than one because Postgres treats NULLs as distinct. If `external_id` is ever "normalised" to `""`, the *second* order in the system fails while a single-checkout test still passes. The same applies to `OrderItem.external_id` (`""` violates `order_item_source_nonempty`).

Concurrent (`pytest.mark.django_db(transaction=True)` + real threads — new infra, first use in this repo, per `docs/TESTING.md:17`). Drive these at the **service** layer — two threads calling `services.checkout(user, key, item_ids)` — not through the test `Client`: `Client` isn't thread-safe and each client carries its own session, so two threads cannot share one session key through it. View-level idempotency is covered sequentially by the replay tests above. Each thread must `connection.close()` in a `finally`, or the test leaks connections and hangs instead of failing. Cases: two simultaneous checkouts with the same idempotency key → exactly one `Order` persists and both calls return it (assert the outcome, not which internal path produced it — either the `IntegrityError`-savepoint catch or the locked-refetch re-check in services.py step 4 may fire depending on timing); two simultaneous checkouts by *different* users racing for the last unit of stock → exactly one succeeds, the other raises `InsufficientStockError`, stock never goes negative.

## Known accepted edge cases (documented, not addressed this batch)

- **Session save races can transiently resurrect a cleared idempotency key/pin.** Django's default session backend overwrites the whole session on save rather than merging; a slow `POST` that clears `checkout_idempotency_key`/`checkout_item_ids` and a concurrently-open `GET` that loaded the session before that clear can race, and the `GET`'s stale snapshot can briefly resurrect the cleared state on save. Not exploitable: the very next `GET /checkout/` sees an empty cart (the order already committed) and clears the stale key/pin again via the existing empty-cart branch. No double-order or lost-order path exists through this.
- **A resurrected key plus an identical re-add returns the original order instead of charging again.** If the session race above keeps a dead key alive *and* the user re-adds exactly the same products and quantities, the recomputed fingerprint matches the old order, so services step 2 returns that order and the view redirects to its receipt — leaving the freshly re-added items in the cart, uncharged. Nothing is lost or double-charged, and it is arguably exactly what `SCHEMA.md` mandates ("equivalent retry returns the original order"); recorded here so it isn't later mistaken for a bug.
- **A bug in the stock recheck would surface as a raw `IntegrityError`/500, not a clean error page.** `bulk_update()` skips per-instance validation, so if the under-lock recheck ever had a bug that let a decrement go negative, the DB's own check constraint would reject it as an unhandled exception rather than a graceful 409. This shouldn't be reachable given the recheck in services.py step 4; if it ever fires, it indicates a logic bug elsewhere worth fixing directly rather than papering over with a catch-all.
