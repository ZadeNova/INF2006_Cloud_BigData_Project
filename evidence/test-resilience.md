## Read these limits before the numbers

1. **One repeat per condition (n = 1).** Every difference between A and B is "indicative, n = 1"; no variance is known and no winner is claimed from these runs alone.
2. **The replacement test is a graceful removal** (ADR-017: A asks the Auto Scaling group to terminate the instance, B stops one task; each is drained from the load balancer first). It is not a crash, a network cut or a bad deployment. "Removal seen" is the drain becoming visible in `targets.jsonl`; a crashed instance would be found by the health check, which is set to 10 s intervals and 3 failures on both variants (`src/infrastructure/modules/web-entry/alb.tf`), about 30 s, and that was not measured.
3. **The database could not be reset between variants for CPU credits and cache.** The credit balance stayed at 576 during A and during B (`cloudwatch/rds_cpu_credit_balance.csv` in each saturation folder), so no run was slowed by exhausted credits. The shop data was reset twice on each variant (`raw/OPS_*_reset-*`), but the resets fell differently: A was reset between the replacement and saturation runs, B only after its saturation run, so B's saturation ran with the orders of its earlier runs still in the database.
4. **The scaling target is low.** The target-tracking policy is 300 requests per target per minute (ADR-011), set before any data: that is 5 requests per second, against a measured ceiling of 118.8 (A) and 105.5 (B) requests per second for one unit (about 4 to 5 percent). Scale-out fired while the CPU series peaked at 14.56 percent on A (`cloudwatch/ec2_cpu_max.csv`) and 14.04 percent on B (`cloudwatch/ecs_cpu_max.csv`). It scales early, which is safe but expensive, and it means the scale-out times say little about a CPU-bound scale-out.
5. **The 3D models are not fetched by the load test.** The shop serves 12 model files (about 15 MB) itself; the load test fetches pages and the ordinary static files only. Real visitors would put more load on the unit.
6. **The ladder (10 and 100 users) was dropped for time.** The saturation run (steps of 1, 2, 4, 8, 16, 32, 64, 128, 256, 512 users, edited into `run.py` on the generator) replaced it. The saturation runs on both variants, and the B scale-out and replacement runs, record `git_dirty_harness: true` in `run.json`. There is no think-time latency at 10 or 100 users.
7. **Different hardware, as far as the files show.** A ran on a `c5.large` whose CPU was an Intel Xeon Platinum 8124M at 3.0 GHz; B's task size is 2 vCPU / 4 GB and the CPU read once from a one-off task was an Intel Xeon Platinum 8259CL at 2.5 GHz (`cpu.json` in each run folder; the tasks that served the load may differ). The slower clock is a possible contributing explanation for B's lower ceiling and cannot be separated from the platform with n = 1.
8. **Two sessions, two days.** A ran on 8 October and B on 9 October, from the same kind of generator (`c5.large`, us-east-1); the B session has a gap of about three hours between the replacement run (ended 03:32 UTC) and the saturation run (started 06:23 UTC), and the first capacity-pin plan before the saturation run failed with AccessDenied errors citing an explicit deny from the lab's `voc-cancel-cred` policy (`raw/OPS_2026-10-09_fargate_pin-1-1-1-count_plan.txt`; the name suggests cancelled lab credentials) and was rerun.
